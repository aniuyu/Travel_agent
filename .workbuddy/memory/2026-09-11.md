### 修复后端既有 bug：/chat 直接报错
- 现象：连上 /chat 发送消息后立刻收到 `[ERROR] asyncio.run() cannot be called from a running event loop`
- 根因：`app.py` 的 `websocket_chat` 里 `from agent import agent` 是懒加载，但它在 **async 处理器内**执行；
  `content/all_agent.py` 模块级 `AllAgent()` → `_get_tools()` → `content/mcps/travily_search.get_tools()` 里用了 `asyncio.run()`
  → FastAPI 事件循环已在运行，报错
- 修复：改为**在子线程里导入**（子线程无运行中的循环，asyncio.run 可用），并加锁缓存复用：
  ```python
  _agent = None
  _agent_lock = asyncio.Lock()
  def _load_agent():
      from agent import agent
      return agent
  async def get_agent():
      global _agent
      if _agent is not None: return _agent
      async with _agent_lock:
          if _agent is None:
              _agent = await asyncio.to_thread(_load_agent)
      return _agent
  ```
  既保持「启动快、首条消息才加载」，又不再崩

## 修复：收起态悬浮钮拖不动（上一轮遗留 bug）

### 现象
- 用户反馈「AI 助手」悬浮小圆钮没有拖动效果

### 根因（两个）
1. **主因**：`startDrag` 里有 `if (e.target.closest("button")) return;`
   —— 这行本意是让面板顶栏的「清空/收起」按钮不触发拖拽，但收起态的悬浮钮**本身就是一个 `<button>`**，
   所以 pointerdown 命中的 target 就是它自己 → `closest("button")` 命中 → 直接 return，拖拽从未开始
2. **隐患**：`startDrag` 里调了 `e.preventDefault()`。对 pointerdown 调 preventDefault 可能抑制兼容鼠标事件，
   导致 `<button>` 的 click 不触发（收起态靠 click 打开面板）→ 会变成「点也点不开」

### 修复
- `startDrag(e, allowButton = false)` 增加放行参数；收起态悬浮钮用 `startDrag(e, true)`，
  面板顶栏仍用默认（排除内部按钮）
- **去掉 `e.preventDefault()`**；防选中改由 `select-none` 类 + 拖拽期间 `document.body.style.userSelect = "none"` 承担
- 悬浮钮补 `touchAction: "none"`（触摸设备上不被滚动手势抢走）与 `select-none`
- 加 **4px 移动阈值**：`Math.hypot(dx, dy) < 4` 时不算拖拽也不位移，
  避免点击时手抖被判定为拖动、导致点不开面板

### 最终交互语义
| 操作 | 结果 |
|------|------|
| 拖动 > 4px 后松手 | 移动位置，**不**打开面板（`movedRef` 拦截 click） |
| 原地点击（< 4px 抖动） | 正常打开面板 |
| 拖动面板顶栏 | 移动面板（顶栏内按钮除外） |
| 位置 | 存 `localStorage["fy_chat_pos"]`，刷新恢复；始终收敛在视口内 |

### 通用教训
- 给「自身就是按钮」的元素加拖拽时，别用 `closest("button")` 做排除判断，要显式传参区分
- Pointer Events 拖拽里慎用 `pointerdown` 的 `preventDefault()`，它会波及 click；优先用 CSS 防选中

| 能力 | 说明 |
|------|------|
| 悬浮 | `position: fixed`，不占布局 |
| 拖动 | 头部把手 + 收起态圆钮，4px 阈值区分点击/拖动，位置持久化 |

### 关键教训（LangGraph astream 双流）
- `stream_mode=["updates","messages"]` 会同时产出：**updates（节点/中间件状态字典）** 和 **messages（AI token 增量）**
- 客户端必须**只把 messages 的 token 当正文**；updates 一律丢弃（或仅作兜底）
- 判断依据应是「能否解析为 JSON 对象」，而**不是**「是否含 messages 字段」——中间件更新没有 messages

## 修复：对话回复时页面抖动 / 渲染 bug

### 现象
- AI 回复过程中面板内容抖动、渲染异常

### 根因（四个叠加）
1. **每个 token 都触发一次全量 Markdown 重渲染** —— `accRef.current += data; upsertAi(...)` 直接 setState，
   而 `markdown` 的 `components`/`remarkPlugins` 是**行内对象**，每次渲染引用都变，
   导致所有历史消息跟着重新解析（长回复时每秒上百次重排 → 抖动/卡顿）
2. **打字气泡与正文气泡同时存在** —— 条件是 `sending && ...`，第一个 token 到达后 `sending` 仍为 true，
   于是「三点气泡」和「正在流式的正文」同时显示，`[END]` 后气泡消失 → 内容跳动
3. **滚动条出现/消失导致宽度突变** —— 消息区 `overflow-y-auto`，内容超过高度时滚动条出现，
   内部宽度骤减，所有气泡重新折行 → 视觉抖动
4. **滚动链** —— 内部滚到顶/底会把滚动传给外层页面

### 修复
1. **节流渲染**：`accRef` 累积 + `scheduleFlush()` 用 `setTimeout(60ms)` 合并刷新，最多约 16 次/秒；
   收尾时 `clearFlushTimer()` 后直接落最终内容
2. **`upsertAi` 内容未变则返回原数组**（`prev[idx].content === text` 直接 return prev），避免无谓渲染
3. **Markdown 渲染抽成模块级 memo 组件**：
   - `REMARK_PLUGINS` / `MD_COMPONENTS` 提到模块作用域（引用稳定）
   - `MarkdownBody = memo(...)`、`MessageRow = memo(...)`，未变化的历史消息整条跳过重渲染
4. **打字气泡条件改为「还没收到第一个 token」**：
   `sending && !msgs.some(m => m.id === aiMsgIdRef.current && m.content.trim())`

## 修复：AI 回复时出现两个气泡（空气泡 + 打字气泡）

### 现象
- 用户截图：发送消息后出现**两个 AI 图标** —— 一个是空气泡，一个是三个点的打字气泡

### 根因（已实测确认）
- 后端 `/chat` 流的前两个 token 实测是 `'\n\n'` 和 `'\n\n'`（**纯换行**）
  （探针输出：`[0] '\n\n'`、`[1] '\n\n'`、`[2] '你好'` …）
- 第一次节流刷新（60ms 后）时，`accRef` 里只有换行 → 仍然 `upsertAi("...")` 创建了 AI 消息
  → 渲染成一个**空白气泡**
- 同时打字气泡的显示条件是 `sending && 没有非空内容`，空白字符 `trim()` 后为空 →
  条件成立 → 打字气泡**也没隐藏**
- 于是两个 AI 气泡并排出现

### 修复
1. `scheduleFlush()` 的回调里加判断：`if (!accRef.current.trim()) return;`
   —— 只有空白时**不创建气泡**，等真正内容到达再渲染
2. 刷新/收尾时用 `trimStart()` / `trim()` 去掉前导换行，
   避免 `whitespace-pre-wrap` 把开头的空行渲染成多余留白
   - 流式中：`upsertAi(accRef.current.trimStart())`
   - 收尾时：`upsertAi(accRef.current.trim())`

### 效果
- 发送后只显示「打字气泡」，第一个有意义的 token 到达时，它被替换成正文气泡（不再有空气泡）

### 通用教训
- 流式渲染要区分「累积内容」与「可展示内容」：**空白字符不应触发创建消息气泡**
- LLM 回复常以 `\n\n` 开头，展示前 trim 很必要（尤其配合 `whitespace-pre-wrap`）

## 对话支持手动暂停 / 终止

### 后端改造（app.py 的 `/chat`）
- **原来**：`while True: data = await websocket.receive_text()` 直接在主循环里读消息
  → 生成期间**无法**收到新消息，所以做不了「终止」
- **现在**：拆出并发 `reader` 任务专门收消息，查询入 `asyncio.Queue`，终止信号置 `stop_event`
  ```python
  async def reader():        # 并发读
      raw = await websocket.receive_text()
      if msg.get("type") == "stop": stop_event.set()
      else: await inbox.put(msg)
  reader_task = asyncio.create_task(reader())
  # 主循环
  msg = await inbox.get()    # None = 断开
  stream = agent.astream(...)
  async for chunk in stream:
      if stop_event.is_set(): stopped = True; break
      ...
  finally:  # 被终止时主动 aclose，尽快释放底层任务
      if stopped and hasattr(stream, "aclose"): await stream.aclose()
  await websocket.send_text("[STOPPED]" if stopped else "[END]")
  ```
- 附带好处：`reader` 先启动，客户端不必等 agent 加载完（约 12s）才能发消息
- 新增协议：客户端发 `{"type":"stop"}` → 服务端回 `[STOPPED]`

### 前端（ChatDock.tsx）
- 生成中把「发送」按钮换成 **⏸ 暂停/继续** + **⏹ 终止**（红色）两个按钮，
  并在输入框下方加固定高度状态条（避免出现/消失时消息区跳动）：
  - 生成中：`⟳ 正在生成… 可暂停或终止` + 右侧「终止」文字按钮
  - 暂停中：`⏸ 已暂停显示（后台仍在生成，点继续可恢复）`
- **暂停**＝冻结渲染：`pausedRef` 为真时 `scheduleFlush` 直接 return，
  token 仍继续累积到 `accRef`；点继续时一次性补上（服务端不受影响）
- **终止**＝真正停下：发 `{"type":"stop"}` + 立即用已收到内容收尾（追加 `_（已终止生成）_`）
- 用 `stoppedRef` 忽略终止后的残余消息；收到 `[STOPPED]` 只复位标记，**不触发 finalize**
  （放在判断最前面，避免上一轮的残余 `[STOPPED]` 打断新一轮）
- `send()` / `finalize()` 里都会复位 `pausedRef` 与 `stoppedRef`

### 验证
- **终止**：发长文查询 → 收 23 个 token → 发 stop → **0.04s 收到 `[STOPPED]`，之后 0 个残余 token** ✅
- **回归**：同一连接连续两轮普通对话均正常 `[END]`（"你好"→"你好！有什么可以帮你的吗？"、"1+1等于几"→"1+1=2"）✅
- 页面 200，TS 编译零错误

### 注意
- 改 app.py 后**必须重启 uvicorn**（已重启）
- 「暂停」只冻结前端显示，服务端仍在生成；要真正省算力请用「终止」
